## Phase 10B.1 Windows linkage proposal

XboxXBERecomp at `767a8183`, BLACK V3 and SCDA V3 use bundled Clang and LLD. Their first-launch link uses `/dll /noentry /nodefaultlib`, the translated objects and a project-produced import library for the host executable's exports. Their release scripts stage app-local release CRT DLLs for the host or tools. Source inspection establishes the linkage design. HTTP range requests could not retrieve the official ZIP directories for an independent archive inventory. [SDK CMake](https://github.com/TGP482/XboxXBERecomp/blob/767a81837fba2d86913f6af81a10b33661d35518/cmake/XbeRecomp.cmake) · [SDK runtime link](https://github.com/TGP482/XboxXBERecomp/blob/767a81837fba2d86913f6af81a10b33661d35518/runtime/app/game_code.cpp) · [BLACK V3](https://github.com/TGP482/BLACK-XBERecomp/blob/V3/src/app/game_code.cpp) · [SCDA V3](https://github.com/TGP482/SCDA-XBERecomp/blob/V3/src/app/game_code.cpp)

The Bulletproof guest already uses these PE link flags and passes gameplay services through `XbeBindGuest`. Its generated SEH regions and `XbeProbeGuest` require MSVC-compatible C++ unwind across the DLL boundary. Preserve the x64 MSVC target, guest exports, service table and the same compatible dynamic exception runtime in both modules.

1. In a later Windows build, inventory undefined symbols in the guest object files with `llvm-nm --undefined-only` and inspect the linked guest's PE imports and unwind data with `llvm-readobj`. Account for the symbols supplied by each of the three libraries before replacing them.
2. Prototype a narrow, project-generated COFF import library from audited `.def` files using bundled LLD. Use only required imports from authorized app-local release VC runtime DLLs and the system UCRT or its supported API-set contracts. Preserve function and data import semantics. For required native helpers outside those exports, audit their ABI and use an independently licensed implementation where available. Check startup, stack probing and any static or TLS initialization before dropping `msvcrt.lib`. This design would omit all three Microsoft SDK and Build Tools archives if each required symbol is accounted for. [Microsoft CRT library roles](https://learn.microsoft.com/en-us/cpp/c-runtime-library/crt-library-features) · [LLVM object inspection](https://llvm.org/docs/CommandGuide/llvm-readobj.html)
3. Validate on Windows 11 without development tools or network access. Check first-launch local compilation, PE imports and unwind records, `XbeProbeGuest` in both throw directions including cleanup, the real Lua continuation, startup and cache reuse. Retain eligible DLL notices and refresh the preparation cache fingerprint for the new inputs.

## Phase 11B Windows linkage implementation

The reference link was traced with LLD using the translated COFF objects, `llvm-nm --undefined-only`, a link map and `llvm-readobj`. The three development archives contributed the following inputs.

| Archive | Resolved references |
| --- | --- |
| `msvcrt.lib` | `_fltused`, `type_info` vftable and its scalar/sized delete chain. The reference link also selected `_load_config_used` and its security-cookie and guard support objects. The resulting load configuration had `GuardFlags` zero and no CFG function table. The guest objects did not reference `__chkstk` or a CRT entry point. |
| `vcruntime.lib` | `_CxxThrowException`, `__CxxFrameHandler3`, `memcpy`, `memmove`, `memset` from `VCRUNTIME140.dll`. The reference load configuration also pulled `__guard_memcpy_fptr` from `softmemtag.obj`. |
| `ucrt.lib` | `atan2`, `cos`, `exp2`, `fmod`, `frexp`, `ldexp`, `log2`, `sin`, `sqrt`, `sqrtf`, `tan` through the UCRT math API set, plus `free` through the heap API set. |

The Windows portable target generates three narrow COFF import archives from `sdk/linux/cmake/windows_guest/`. They retain the same dynamic VC exception and UCRT import contracts. `portable_guest_crt.cc` defines `_fltused` and emits the local MSVC-layout `type_info` vftable and deleting destructor for exception descriptors. Only that source is built with `-fno-rtti`, which avoids recursive emission of RTTI for the CRT's own class in Clang. The bridge and guest partitions retain their exception metadata and compile settings. The DLL uses `/dll /noentry /nodefaultlib`. Hashing the host and all packaged compiler files automatically separates the new cache from the reference cache.

The packager uses the generated archives by default. Providing both `-MsvcLib` and `-UcrtLib` explicitly stages the original linkage for comparison. Release CRT DLLs from the licensed x64 REDIST location and their provenance are still required, and Windows 11 supplies the system UCRT. The remaining publication gates above still apply. [Microsoft UCRT deployment](https://learn.microsoft.com/en-us/cpp/windows/universal-crt-deployment)

### Windows 11 validation

- Release `BULLETPROOF_PORTABLE_ONLY` built with exclusive handles preventing access to the original ISO and XBE. Its fresh build graph generated the title metadata and PE bridge without any translated partitions. The separate `Bulletproof` static target also built successfully.
- Both guest links produced AMD64 DLLs with the same imported symbol set, ASLR, NX and SEH unwind metadata. Both had a zero entry point and no TLS table. The two fewer SEH entries in the new DLL correspond to the replaced native CRT code. The Win64 round trip through `XbeProbeGuest` verified C++ cleanup on both sides for both links. A directed Lua test invoked the actual translated `luaD_throw` through the PE module and the production Lua hooks. It verified the protected call caught status 2, restored `errorJmp`, the stack and callee-saved registers, and accepted a subsequent protected call.
- The test ZIP contained no Microsoft SDK or Build Tools `.lib` files, disc data or translated guest. Its first run used a network-restricted session and a system-only `PATH`, with the SDK and compiler environment omitted. It compiled 67 units using bundled tools and published the guest at 61.54 s. The restricted session could not create the Vulkan swapchain. The interactive Windows relaunch reused the same DLL at 0.70 s and initialized Vulkan. This checks first-launch independence from external tools on the test host. A clean Windows VM without installed development tools has yet to be tested.
- The interactive run showed the introductions, the PDA and the opening mission, accepted keyboard and mouse input and gave a nonzero WASAPI signal in 30 of 30 samples. It exited with code 0. The native Windows save and portable storage test passed directory layout, migration, failed rename, atomic replacement, reopen and concurrent I/O. In-game checkpoint creation and reload, and controller input, were outside the completed checks.

## Phase 12B redistribution decisions

### Title and XDK metadata

**Confirmed.** The title TOML is reproducible from the supported disc as documented above. The two 5849 tables are byte-identical to the pinned upstream copies distributed with the SDK's MIT notice. Carry the SDK notice with any authorized copy. The layout is a host build and first-launch input. The signatures are a scanner input. The current binary archives stage only the layout of those two tables, and the hosts compile values derived from the title TOML. Removing the visible TOML or signature file from an archive alone leaves the embedded metadata and the runtime's preparation requirements in place. [Pinned MIT notice](https://github.com/TGP482/XboxXBERecomp/blob/cc9edda3a821a4204dc28783f429b88a27ade4f9/LICENSE) · [Pinned tables](https://github.com/TGP482/XboxXBERecomp/tree/cc9edda3a821a4204dc28783f429b88a27ade4f9/xdk/5849)

**External review.** Have a qualified reviewer assess the actual address, layout and fingerprint data, how they were obtained, applicable disc or SDK terms and the jurisdictions for distribution. Obtain permission where needed. The EU judgment in *SAS Institute v. World Programming* distinguishes functionality and file formats from protected expression. Its holding about formats does not determine the rights in these particular table contents or derived fingerprints. If clearance is unavailable, keep the title and XDK data and any binaries embedding them private. A future public path can resolve them locally from the player's copy using cleared scanner inputs. That would require changing the host metadata path and validating first-launch generation. Local generation is not itself a clearance for any scanner inputs it distributes. [CJEU judgment, C‑406/10](https://eur-lex.europa.eu/legal-content/EN/TXT/?uri=celex%3A62010CJ0406)
